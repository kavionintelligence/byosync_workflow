FOUR ACTORS IN THE DIAGRAM
--------------------------
  1) USER PHONE        — Enrollment, biometrics, consent UI, signing.
  2) BYOSYNC CONTROL PLANE — Identity registry, policy, tokens, KMS, audit;
                            receives auth primitives and orchestrates consent;
                            does NOT store personal KYC in the vault path.
  3) USER VAULT (cloud) — Encrypted personal data & payment tokens;
                          ciphertext + wrapped DEKs; direct from phone on
                          enroll/update (ByoSync excluded from PII path).
  4) COMPANY DESKTOP   — Partner console; sends requests; receives proofs
                          (boolean JWS, SCA proof, webhooks); no PII by default.

CORE SEPARATION (ARCHITECTURE SUMMARY — vault_inception header in source)
---------------------------------------------------------------------------
  ByoSync DB receives:
    • Auth primitives only (helper_data, k2 commitment / derivative,
      device public key, pseudonymous user_token, encrypted vault pointer).
    • Later: consent ledger entries, boolean assertion / audit metadata,
      signed proofs — not underlying field values.

  User vault receives:
    • ALL personal data fields (name, phone, email, DOB, address, KYC, etc.)
      encrypted per-field (DEK per field, UMK wraps DEKs), sent DIRECTLY
      from phone to vault. ByoSync is NOT in this data path.

  Boolean / consent flows:
    • ByoSync may fetch ciphertext from vault, compute answer in enclave,
      sign JWS for company; plaintext wiped after compute.

SCENARIO 00 — VAULT INCEPTION (one-time setup) — 9 steps
================================================================================
Purpose: Register once with strict separation — auth → ByoSync; PII → vault.

Step 01/09 — First launch — nothing stored yet
  Flow: Phone (local UI only). Desktop may show “waiting”.
  Narration: First open; itemised notice before capture; nothing stored yet.
  Dossier: Zero-state start — DPDP notice before collection.

Step 02/09 — Face + voice enrollment — on-device fuzzy extractor
  Flow: Phone only (camera/mic → fuzzy extractor → helper_data + k2; raw zeroed).
  Narration: Biometrics never leave device; helper_data non-reversible.

Step 03/09 — Secure Enclave generates random User Master Key (UMK)
  Flow: Phone Secure Enclave — random UMK; wrapped with k2 + device key;
        face authorises release, does not derive UMK.

Step 04/09 — Auth primitives → ByoSync DB · vault pointer registered
  Flow: PHONE ──(TLS, auth primitives only)──► BYOSYNC
        BYOSYNC ──(e.g. token issued / ack)──► COMPANY DESKTOP (illustrative)
  Payload idea: device_pubkey, helper_data, k2_commitment, vault_ptr_enc,
                nonce, attestation → response user_token. No name/phone/email.

Step 05/09 — KYC data → encrypted on device → DIRECT to vault
  Flow: PHONE ──(ciphertext + wrapped DEKs, direct PUT)──► USER VAULT
        (No path through ByoSync for plaintext PII.)
  Narration: Per-field DEK, AES-GCM, UMK wraps DEKs; ByoSync not in path.

Step 06/09 — Vault inception complete · two separate stores
  Flow: Conceptual — two stores: ByoSync (auth) + vault (PII ciphertext).
  Phone still holds wrapped_UMK / keys in Enclave.

Step 07/09 — Future: boolean assertion tokens → ByoSync DB
  Flow (illustrative): BYOSYNC ◄──► VAULT (fetch ciphertext / return blob);
        assertions & audit hashes live in ByoSync DB — not raw PII.

Step 08/09 — Why this order is better — comparison
  Flow: N/A (educational). Wrong: phone → ByoSync → vault (ByoSync sees PII).
        Right: phone → vault direct + phone → ByoSync auth only.

Step 09/09 — Vault inception done → all scenarios ready
  Flow: Foundation set; switch to other scenarios for consent flows.
